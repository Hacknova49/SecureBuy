# SecureBuy Current State

**Audit date:** 2026-09-12  
**Audited commit:** `eb3c0bce`

## Executive summary

SecureBuy is a React/Vite frontend with a small Express/Mongoose backend. The current implementation is a functional prototype for device-bound event tickets, rotating ticket tokens, event creation, ticket purchasing, scanning, and Gemini-powered event assistance. Signed bearer sessions, protected routes, recovery, and server-issued rotating tokens were added after this audit; payment, atomic inventory, rate limiting, and full production hardening remain outstanding.

## Implemented user flows

### Authentication and device binding

- `POST /api/auth/login` creates or loads a user by email.
- New attendee accounts are bound to a randomly generated browser device ID.
- A recovery code is generated for new users and displayed once in the frontend.
- Login from a different attendee device returns `403 Device mismatch`.
- `POST /api/auth/recover` validates a time-limited recovery-code hash and rebinds the device.
- Login and recovery now return a signed, 24-hour bearer token; the frontend stores it alongside the user object in `localStorage`.

### Events

- `GET /api/events` returns all events.
- `POST /api/events` creates an event from request body data.
- The frontend provides manager event creation and Gemini-generated event copy.
- Event creation now requires a signed manager session.

### Ticket purchase

- `POST /api/tickets/purchase` checks event existence and inventory, creates a ticket with a random secret, binds it to the submitted device ID, and increments `soldTickets`.
- Checkout loops through cart quantities and performs one purchase request per ticket.
- Inventory updates are not atomic, so concurrent purchases can oversell an event.
- There is no payment provider or payment verification.

### Ticket display and scanning

- `GET /api/tickets/:userId` requires authentication and restricts attendees to their own tickets.
- `SecureQR` displays a QR image generated by the external `api.qrserver.com` service.
- `GET /api/tickets/:ticketId/token` issues the current server-derived 15-second token only to the ticket owner on the bound device.
- `POST /api/tickets/scan` requires a manager session, checks active status, accepts a small clock-drift window, and atomically marks a valid ticket as used.
- The scanner UI currently accepts manual `TICKET_ID::TOKEN` input; camera decoding is not wired into the flow.

### AI features

- `POST /api/ai/hype` generates event descriptions.
- `POST /api/ai/chat` sends event context and a user message to Gemini.
- The Gemini API key is required at backend startup and is proxied from the backend rather than intentionally exposed by the API client.
- Inputs are passed into prompts without validation, length limits, abuse controls, or tenant/user authorization.

## Data model

### User

`name`, unique `email`, optional `avatarUrl`, hashed/time-limited recovery fields, and `role` (`USER` or `MANAGER`).

### Event

`name`, `description`, `date`, `venue`, `price`, `image`, `tags`, `organizerId`, `totalTickets`, and `soldTickets`.

### Ticket

`eventId`, denormalized event information, `userId`, `status` (`ACTIVE`, `USED`, or `REVOKED`), hidden `seedSecret`, and `purchaseDate`.

## Build and validation status

- Backend `npm run build`: **passes**.
- Frontend `npm run build`: **passes**.
- No automated test suite was found in the repository.
- Dependency installation reports known audit findings: 9 backend vulnerabilities and 15 frontend vulnerabilities at audit time. These were not auto-fixed because forced upgrades could introduce breaking changes.

## Highest-priority gaps before production

1. Replace the prototype email-only login with verified passwordless authentication and rotate short-lived access/refresh tokens.
2. Add recovery attempt rate limits, audit logging, and a migration for any legacy plaintext recovery fields.
3. Replace the prototype SHA-256 time-window token with standards-compliant TOTP or a signed, nonce-based ticket token.
4. Add venue/event scoping to manager scan authorization and audit every scan.
5. Make inventory reservation and purchase idempotent and atomic; add payment integration before issuing tickets.
6. Mark tickets used atomically during scan and reject already-used/revoked tickets.
7. Add request validation, rate limiting, structured errors, security headers, restricted CORS, audit logs, and monitoring.
8. Remove or consolidate the duplicate `dataService.ts` client and define one environment-driven API base URL.
9. Replace the external QR image dependency with an in-app QR renderer or a controlled backend/static asset path.
10. Add unit, integration, and end-to-end coverage for auth, purchase, token rotation, scanning, inventory, and recovery.

## Recommended next implementation slice

Start with the backend foundation: request validation, authentication/authorization middleware, a consistent environment configuration, and a secure ticket-token contract. Then add atomic inventory and scan state transitions before expanding product features.
